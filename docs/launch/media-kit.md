# Share Own The Change

Own The Change helps developers explain the code their AI agent changed. This kit gives you an image, accurate descriptions, and links you can share without access to anyone's project or learning records.

## One-line description

An open-source Claude Code and Codex plugin that turns an AI-generated diff into a change debrief you can revisit.

## Short social post

The text below is a draft, not a record of a post being published:

```text
Your AI changed the code. Can you explain why?

Own The Change adds change debriefs to Claude Code and Codex: what changed, why, and what tests missed. Open source; local Markdown records.

Try the demo: https://github.com/parkyountaek/own-the-change
```

## Longer developer post

The text below is also a draft. Publish it only through an authorized account in a community where it fits:

> Tests pass. But could you explain the AI-generated change in a pull request, or find where to start a related fix next week?
>
> I'm building Own The Change for that moment. After a coding task, run a Change Debrief in Claude Code or Codex. It uses the actual diff and test evidence to explain decisions, gaps, and where to look next, then saves a local Markdown record. Understanding questions are optional.
>
> You can install it with plugin commands, without manually cloning this repository. A small synthetic demo lets you try it without sharing work code.
>
> It is experimental, and I have not measured a long-term learning benefit. I'm looking for feedback on installation, the debrief itself, and whether you'd use it on another task.
>
> Built with development assistance from Codex. Independent community project; no separate server or API key, and your coding agent's existing data policies still apply.
>
> Try it: https://github.com/parkyountaek/own-the-change

Use "I'm building" only if you represent the project; otherwise change it to "I found." For a longer community submission, see the [Show HN draft](recruitment.md#show-hn-draft).

## A small, measurable launch

1. Start with a GitHub announcement and the [first-use trial](early-access.md). Ask what became clearer and which step was confusing.
2. Choose one external developer community, check its current promotion rules, and post one tailored introduction with the synthetic demo. See the [release checklist](../releasing.md) before broader outreach, including the unresolved private conduct-reporting contact.
3. Invite an optional return on a second task within a week. Do not collect private records or chase people who decline.
4. Fix the most frequently reported installation or action-selection problem before expanding to more channels.

Keep any tally manual and aggregate: first-use reports, installation failures, and voluntary reports of a second use. These are not telemetry, verified active-user counts, or learning-outcome measurements. Do not infer adoption from stars or invent testimonials.

This kit does not authorize paid advertising, bulk messages, coordinated votes, or posts from someone else's account. External drafts remain unpublished until a channel and account are chosen. See [directory submission preparation](directory-submission.md) for the separate vendor application status.
